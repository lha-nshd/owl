Every results table across the OWL — Search Data Dictionary, Browse by Category, and Popular Variables — uses the same basket controls, so once you've learned them on one page, they work identically everywhere else. This page walks through each control in detail: adding variables one at a time, the Add All button and its different states, syncing linked sweeps automatically, using pagination to add larger numbers of variables in fewer clicks, reviewing or exporting what you've collected, restoring or bulk-adding to a basket by uploading a file, and what happens when a basket goes over 500 variables.

Adding a single variable

Every row in a results table has a checkbox in the leftmost Add variable column. Ticking it adds that variable to your basket immediately — there's no separate confirmation step or save button to click afterward.

  • Instant feedback — the checkbox stays ticked once a variable is added, so you can see at a glance which rows on the current page are already in your basket.
  • Untick to remove — clicking a ticked checkbox removes that variable from the basket again, the same way it was added.
  • Header counter — the basket icon in the site header updates its running total the moment you tick or untick a row, so you don't need to open the basket page to confirm something was added.

This is the right approach when you're working through a short, specific list of variables you already know you want, rather than adding everything a search or category returns.

Longitudinal Search adds variables a little differently, since each row there represents a whole Field ID rather than a single variable. Clicking View on a row expands a detail panel where you can add every sweep to your basket in one click, or tick individual sweeps within that panel — there's no plain row checkbox to use directly, because the choice of which sweep(s) to add happens inside the expanded view instead.

The "Add All to Basket" button

Above every results table sits an Add All to Basket button, which adds every variable currently visible on the page in a single click rather than ticking each row individually. The button changes appearance and label depending on the state of the table:

Add all visible variables — teal, the default state. None, or only some, of the variables currently visible are in your basket yet.
Remove all visible variables — red, once every variable currently visible has already been added to your basket.
No visible variables to add — black, disabled. Your search or filters have returned zero matching rows, so there's nothing to add.

This toggle behaviour means the same button always reflects the current state of the table — you never need to check the basket separately to know whether the button will add or remove variables.

Syncing linked sweeps

Some variables are collected identically — the same question text and coding — across two or more sweeps. These are the variables Longitudinal Search groups by Field ID rather than listing one row per sweep, and their individual sweeps (wt50u, wt52u, wt53u, and so on for a single measure like weight) are what this section calls sibling variables. A toggle next to the basket icon in the site header, visible on every page, controls whether adding or removing one sibling automatically does the same for the rest.

Sync linked sweeps — on, the default. Ticking one sibling adds every other sibling of that variable to your basket too; unticking one removes every other sibling as well.
Sync linked sweeps — off. Each sibling is added or removed strictly on its own, with no effect on the rest.

Every time siblings are added or removed this way, a brief confirmation appears near the basket icon naming which variables changed, with an Undo link that reverses just that action — it doesn't touch anything you added or removed separately. The toggle itself is a persistent setting stored in your browser, the same way your basket is, so it keeps whichever state you last left it in as you move between pages.

This applies wherever a single variable is added or removed — checkboxes on Search Data Dictionary, Browse by Category, Popular Variables, Search by Year, and Documentation pages, the Add All to Basket button above, a document's own "Add all to basket" button, and the Remove button on the basket page itself (see Reviewing and exporting below).

Longitudinal Search doesn't use this toggle. Its own detail panel already lets you add every sweep of a Field ID at once, or tick sweeps individually — since the whole group is already right there to choose from directly, the sync toggle is switched off for actions taken on that page specifically, whatever it's currently set to elsewhere. Ticking a single sweep there adds only that sweep.

Uploading a basket file respects this setting too — see Uploading a basket below for how it works there.

Using pagination to add more at once

The Add All to Basket button only acts on the variables currently visible on the page — not your entire result set. If a search returns 200 variables but your page size is set to 15, clicking Add All adds only those 15.

To add a larger number of variables in fewer clicks, increase the page size before clicking Add All. The page size control sits above the results table and offers options of 15, 30, 50, and 100 rows per page. Setting it to 100 and clicking Add All adds up to 100 variables in a single click.

For result sets larger than 100, you can repeat the process page by page — advance to the next page and click Add All again — until you've worked through the full set. The basket accumulates everything you add across pages, so there's no risk of losing earlier additions when you move to the next page.

Building a basket over 500 variables with Add All is fine — Condor will automatically split it into several baskets when you upload it there. See the Large baskets section below for what this means for how your request is reviewed.

Restricted variables

Some variables carry an access restriction beyond the standard public/sensitive classification — you'll recognise them by the small lock icon next to their name wherever they appear on the site (see Variable status icons). Hovering the lock shows a message specific to that variable, usually naming who to contact to request it.

Restricted variables can be added to your basket exactly like any other variable. The checkbox, the Add All to Basket button, and pagination-based bulk adding (see Using pagination to add more at once above) all work identically whether a variable is restricted or not — nothing on the site stops you from selecting one.

This is a deliberate choice, not an oversight. Blocking restricted variables from the basket wouldn't actually prevent anyone from requesting one — the same result is available by marking Y against that variable directly in an offline copy of the Data Dictionary and uploading it (see Uploading a basket above), which OWL also accepts without checking restriction status. Blocking it in one place while leaving it open in another wouldn't add any real protection — it would just make the two routes behave inconsistently. So OWL treats every variable the same way while you're building a basket, restricted or not, and handles the actual access control at the point where it matters: the formal data request.

What happens at each stage

Restriction status doesn't change anything about how a variable behaves in your basket on OWL itself — only what happens once it leaves OWL and reaches Condor:

Adding to your basket — works exactly as normal. Tick the row, or use Add All to Basket, or upload a marked-up file; a restricted variable is added to your basket the same way any other one is, and shows the same way in your basket page.
Downloading your basket — also works exactly as normal. The exported Data Dictionary marks a restricted variable Y in the Request variable column the same as everything else in your basket — the file itself doesn't distinguish restricted variables from any other kind.
Uploading to Condor — this is the one step where restriction status matters. When your downloaded basket file is submitted as a formal data request through Condor, restricted variables will not be imported automatically along with the rest of your request.
Restricted variables must be requested separately from the rest of your basket. Because Condor won't import them as part of a normal basket upload, you'll need to request each one directly, outside of that upload — who to contact depends on the specific variable, and that contact detail is exactly what's shown when you hover the lock icon next to it. Check every restricted variable in your basket before submitting to Condor, and follow up on each one using the message shown for that variable, rather than assuming the bulk upload has taken care of it.

A practical habit: before uploading to Condor, scan through your basket for any lock icons, note the contact given for each, and send those requests alongside your main submission rather than after — that way you're not waiting on a second round trip once you discover a variable didn't come through.

Restricted variables are pinned to the top of the basket page, ahead of everything else in your list, rather than sitting wherever they happen to fall alphabetically or by the order you added them. This is exactly to make the habit above easier — you don't need to scan the whole basket looking for lock icons; anything restricted is already grouped together at the top, ready to check off before you submit to Condor. A labeled row marks where the group starts ("Restricted variables (N)") and, further down, a quieter divider marks where it ends and the rest of your basket resumes — so if every row on a page happens to be restricted, it's clearly explained rather than just an unbroken block of colour.

Reviewing and exporting your basket

Once you've added variables — individually, in bulk, or a mix of both — the basket page is where you manage the full list. From there you can review every variable you've collected, remove anything you no longer need, and double-check labels and sweep coverage at a glance.

Clicking Remove on a row here uses the same Sync linked sweeps setting as everywhere else. If it's on, removing one sibling from the basket page also removes its other sweeps — not just this one row — with the usual confirmation and Undo.

Downloading your basket doesn't just export your selection — it builds you a fully completed copy of the data dictionary as an Excel (.xlsx) file. Every variable in your basket is marked Y in the Request variable column, ready to use directly in a data access request. You'll be prompted to choose where to save the file, with a sensible filename already filled in. See The Data Dictionary for what every column in the file means.

The basket persists as you move between pages and tools, so a variable added from a category browse will sit alongside one added from a keyword search — there's no need to finish in one tool before switching to another.

Uploading a basket

Your basket is stored locally in your browser — nothing is saved to a server, and no account or login is required to use OWL. That's convenient, but it also means your basket only exists on the device and browser you built it in.

Because the basket lives in your browser's local storage, it can be lost if you clear your browsing data or cookies, switch to a different browser or computer, or use a private/incognito window. If it isn't downloaded, that work is gone for good — there's no way to recover it afterward.

The safest habit is to download your basket regularly as you build it, rather than only at the very end. If something happens to your browser's storage, you can simply upload that same file back in and carry on exactly where you left off — nothing needs to be re-searched or re-added by hand.

What you can upload

The Upload saved dictionary button sits on the basket page, next to Clear Basket and Download pre-filled dictionary. Clicking it opens a panel and prompts you for a file.

What you upload is always the same thing — a copy of the Data Dictionary, with variables marked Y in the Request variable column — it just doesn't matter how that Y got there:

  • Completed on OWL — build a basket on the site as normal, then click Download Basket. The Y marks are filled in for you automatically.
  • Completed manually — if you or a colleague already has a copy of the Data Dictionary and marks Y directly against variables of interest offline, that same file uploads just as easily, without needing to search for or add each variable individually on the site first.

Checks made on the file

Before anything is added, the file is checked over and any issues are reported clearly rather than added or dropped silently:

Missing variable name — rows marked Y with no NSHD Variable Name are skipped and listed by row number, since there's nothing to add without a name.
Invalid Request variable value — anything other than blank or exactly Y in that column (a lowercase y, N, or a stray note, for example) is skipped, and listed together with the variable name and the value that was found, so you can go back and fix the source file.
Duplicate variable names — if the same variable name appears more than once marked Y, only the first occurrence is kept and the rest are listed.
Over 500 variables — a heads-up if adding the file would take your basket over 500 variables. This doesn't block the upload, and you don't need to split anything yourself — Condor automatically divides it into several baskets once you upload it there. See Large baskets below for what this means for how your request is reviewed.
Restricted variable(s) found — a heads-up if any row marked Y in the file is a restricted variable. This doesn't block the upload either; it names each one found, so you know upfront which of your selections will need a separate Condor request before you even click Confirm & Add to Basket.

Each of these appears only when relevant, and starts collapsed with a small "click for details" note next to it — click to expand and see the full list of affected rows or variable names, or leave it collapsed if you just want the headline count.

If restricted variables are found, a separate highlighted banner appears above the results table — distinct from the collapsible checks above — naming each restricted variable in the file. It stays visible for the whole review step, not just as a one-line count, since this is the one check worth seeing at a glance rather than expanding to check.

Reviewing before anything is added

Once the file has been checked, you'll see a summary line — highlighted so it stands out — showing how many variables were found, how many are new, and how many are already in your basket. Below that is a full table listing every variable that will be added, with each row marked either New or Already in basket, styled the same way as the main basket table so it's easy to read.

If your file contains longitudinal variables with sibling sweeps, the preview shows a checkbox — "Also include N linked sweeps of longitudinal variables in this file". It starts matching whatever Sync linked sweeps is currently set to — ticked if the toggle is on, unticked if it's off — and stays in sync live if you flip the toggle while the panel's still open. You can still tick or untick it yourself regardless of the toggle: that's a one-time choice for this upload only, and never changes the toggle itself.
Whenever siblings are found, a box below the checkbox lists them either way. If the checkbox is ticked, it says how many will be added and shows them at the top of the table below. If it's unticked, it instead says they won't be added this time and names the same variables, so you still see what you're leaving out — not just a number, but exactly which ones.

Nothing is added to your basket at this point. You need to click Confirm & Add to Basket to go ahead, or Cancel to close the panel without changing anything. This means you can safely upload a file just to check what's in it, and back out if it isn't the one you meant to use.

Uploading never overwrites your existing basket. Variables already present are left as they are and simply marked Already in basket in the preview — only genuinely new variables from the file are added once you confirm.

Large baskets: automatic splitting on Condor

You no longer need to split a large basket yourself before uploading. If your basket has more than 500 variables, Condor automatically divides it into several baskets when you save — each with no more than 500 — so uploading works the same way regardless of size. This is a convenience for splitting, not a reason to add more than your project actually needs — see below.

How split baskets are reviewed. If your request has been split into multiple baskets, they are reviewed collectively, as one overall request — not as separate, independent submissions. Requests for a large number of variables may take longer to process, since they go through a more thorough risk assessment, which can delay your dataset being created. You may be asked to justify your request if your total comes to more than 500 variables across a single submission, even though it's been split into several baskets.

The 500-variable figure describes the scale a single request is assessed at, not a fixed cap on your project overall — splitting large requests across baskets is fine. But every variable you add still adds to the review, so it's worth keeping each basket to what your project genuinely needs rather than adding variables speculatively.
